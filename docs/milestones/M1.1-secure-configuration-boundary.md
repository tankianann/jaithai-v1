# M1.1 — Establish a Secret-Safe Configuration Boundary

**Status:** In progress

**Delivery phase:** Phase 1 — Clean source recovery

**Roadmap:** [`../roadmap/roadmap.md`](../roadmap/roadmap.md)

## Outcome

The legacy application has a documented, reviewable configuration model in which tracked source contains no real credentials and local or deployment environments supply secret values outside Git.

## Scope

- Inventory every first-party use of database credentials, encryption material, SMTP credentials, SMS credentials, mapping tokens, API keys, payment credentials, and similar secrets.
- Confirm that historical credentials are rotated, revoked, or unusable before any integration is enabled.
- Add repository ignore rules for real environment files, local overrides, logs, caches, generated documents, database volumes, and other runtime state.
- Define a minimal environment-variable contract and commit an example containing safe placeholders only.
- Refactor known secret-bearing CodeIgniter configuration and application helpers to obtain values through the chosen configuration boundary.
- Add clear failure behaviour for missing required configuration where silent fallback would be unsafe.
- Review the complete candidate tree and staged snapshot for secrets.
- Update the security documentation if implementation reveals additional secret classes or locations.

Initial high-risk files include:

- `src/application/config/database.php`
- `src/application/config/config.php`
- `src/application/helpers/onemap_helper.php`
- `src/application/helpers/phpmailer_helper.php`
- `src/application/helpers/sms_helper.php`

The inventory must not be limited to this initial list.

## Constraints

- Do not commit or print current secret values at any point.
- Do not import or attach the historical repository's `.git` data.
- Keep PHP 7.4 and CodeIgniter 2.2.2 unchanged.
- Avoid behaviour changes unrelated to configuration and safe integration defaults.
- Default local behaviour must not send email or SMS, charge payments, call production-only services, or modify production data.
- Do not restore the removed `assets/menupdf/` or `assets/voucher-templates/` directories.

## Acceptance Criteria

- Historical credentials have been accounted for and their rotation or revocation status is recorded without storing their values.
- Real local environment and override files are ignored by Git.
- A tracked example lists every required configuration variable using non-secret placeholders.
- Known database, application encryption, email, SMS, mapping, payment, and integration credentials are no longer hard-coded in the candidate source.
- Missing required values fail safely or leave the corresponding integration explicitly disabled.
- Local defaults cannot trigger production side effects.
- An automated secret scan of the candidate source and staged snapshot reports no unresolved secret findings.
- Manual inspection of the staged diff confirms that only intended sanitized configuration and supporting code are present.
- The security document and roadmap reflect any new findings or decisions.

## Progress

- Added root ignore rules for environment files, local container data, CodeIgniter runtime output, and generated PDFs.
- Added a value-free `.env.example` containing the current environment-variable contract.
- Added a dependency-free environment loader that is initialized before CodeIgniter.
- Externalized the known database, encryption, OneMap, Elastic Email, SMTP, Brevo, Clickatell, and PayPal configuration values.
- Disabled email, SMS, OneMap, and PayPal integrations by default.
- Removed obsolete commented credentials encountered in active configuration files.
- Verified every modified PHP file with the PHP 7.4 CLI image.

- Scanned both commits in the new repository history with Gitleaks v8.30.1 in redacted mode; no leaks were found.

3. Run an approved secret scanner against the complete source candidate.
4. Stage only the intended M1.1 files and run the scanner against the staged snapshot.
5. Inspect `git diff --cached` in full.
6. Run PHP syntax checks on every modified PHP file using the PHP 7.4 runtime when available.
7. Confirm that safe local placeholders load while external integrations remain disabled.

## Exclusions

- Docker runtime construction; that begins in M2.1.
- Database schema or development-data import; that belongs to M2.2.
- Catering-menu changes.
- General refactoring or framework modernization.
