# M2.4 — Safe Development Fixtures

**Status:** Implemented

**Delivery phase:** Phase 2 — Reproducible local runtime

**Roadmap:** [`../roadmap/roadmap.md`](../roadmap/roadmap.md)

## Outcome

A developer can replace all local application rows with a small, deterministic, wholly synthetic data set suitable for authenticated administration, order display, feedback and voucher listings, and PDF-generation checks.

## Scope

- Track synthetic fixtures separately from the production-derived schema.
- Add a guarded, repeatable command that clears local rows before loading fixtures.
- Provide one local administrator, the two required application options, one fake order, one feedback response, and one voucher.
- Use reserved or obviously fake contact details, including the non-deliverable `.invalid` email domain.
- Extend the local smoke suite through administrator login, fixture-backed screens, and timestamp PDF generation.
- Keep all outbound integrations disabled and avoid final order submission or other workflow mutations.

## Safety Boundary

`php bin/seed.php --force` refuses to run outside the `development` environment, against a database not named `jaithai`, without the exact five-table schema, or without the explicit `--force` flag. It loads only the tracked Docker-local configuration when run from the host.

Every fixture is invented for this repository. No production row, customer detail, password, token, auto-increment position, or serialized order was used as fixture source material. The tracked administrator password is intentionally public and local-only.

## Fixture Set

| Table | Records | Purpose |
| --- | ---: | --- |
| `jt_options` | 2 | Next-order number and a synthetic driver list. |
| `jt_users` | 1 | Local administrator authentication. |
| `jt_orders` | 1 | Order dashboard, detail, and document rendering. |
| `jt_feedback` | 1 | Joined feedback listing. |
| `jt_vouchers` | 1 | Voucher listing. |

The local administrator login is `local-admin` / `local-admin-only`.

## Acceptance Criteria

- One documented command replaces local rows with a deterministic fixture set.
- Re-running the command produces the same records and counts.
- The seeder cannot target the production environment or an unexpected database name.
- All fixture identities and contact details are demonstrably synthetic.
- An administrator can authenticate and view the synthetic order, feedback, and voucher.
- A fixture-backed PDF can be generated and served locally.
- Smoke testing does not change fixture row counts or contact external services.

## Verification

Implemented and verified on 2026-10-01:

- Schema reset followed by fixture seeding created six records across all five application tables.
- A second host-side seed replaced the fixture set cleanly, demonstrating repeatability.
- The expanded smoke suite completed 59 checks with zero failures under both host PHP and container PHP 7.4.
- Authenticated dashboard, order-detail, feedback, and voucher pages rendered their fixture markers without PHP errors.
- Timestamp PDF generation produced a reachable file with an `application/pdf` content type and a PDF signature.
- Fixture table counts remained unchanged after the suite.

## Exclusions

- Production data, anonymized production data, and production credentials.
- Final order submission and mutating administrator actions.
- External email, SMS, mapping, payment, and calendar integrations.
- Browser JavaScript and visual-layout automation.
