## Approved Requirements

- Replace the dishes, choices, and add-ons in the targeted legacy menus with the corresponding supplied collection content.
- Use the supplied per-pax prices and minimum order quantities.
- Preserve the existing customer-facing menu names: `Set Catering Menu A–D`, `DIY Catering Menu A–D`, and `Vegan Catering Menu A–D`.
- Do not rename the public menus to Essential, Classic, Signature, or Supreme; those names identify which supplied content tier maps to each legacy letter.
- Treat all twelve targeted menus as non-halal.
- Do not add a “non-halal” label.
- Remove halal claims or labels associated specifically with these twelve menus; leave unrelated site-wide and outlet wording unchanged.
- Do not change or process image assets during this documentation step.

## Dish and Choice Rules

- Each legacy menu must receive the complete numbered dish sequence from its mapped supplied section.
- Fixed dishes remain fixed.
- Every “Choice of” group must remain an explicit customer selection using the supplied options.
- Regular, normal, and vegan variants must retain the supplied wording unless a separate editorial decision is approved.
- “No Animal Ingredients,” fish-sauce, oyster-sauce, garlic-and-onion, and other dietary notes are content requirements and must not be silently removed.
- Supplied per-pax add-ons must affect both displayed copy and price calculation.
- Tako has no additional charge in all three supplied collections.
- Mango Sticky Rice retains the supplied `$1` per-pax add-on.
- DIY drink choices and their supplied add-ons are included in the DIY menu price model.
- Vegan menu drinks remain outside the included courses and use the existing add-on-drink model, as recorded in the vegan source corrections.

## Naming and Compatibility Rules

- Customer-facing names remain the legacy names even when the underlying content is sourced from Essential, Classic, Signature, or Supreme tiers.
- Preserve existing public routes and internal menu IDs for A–C and all existing Set and DIY menus unless implementation proves a compatibility change is necessary.
- Existing cart, saved-order, administrator, email, and PDF views depend on stable menu titles, IDs, and serialized dish data; M3.2 must avoid unrelated schema or historical-order changes.
- At discovery time, Vegan Menu D did not exist as a `VEGED` definition or `vegetarianMenuD` controller route. M3.2C subsequently added that stable fourth vegan menu without repurposing an unrelated mini-party vegan menu.
- Obsolete menu-PDF downloads remain disabled and are not restored by this work.

## Halal-Language Boundary

The targeted menu source documents do not contain halal claims. The current code search found general-site halal references in the home page and outlet labels, but those references are outside this menu-update scope.

M3.2 must remove any halal wording found on the twelve menu cards, detail pages, descriptions, metadata, terms, or their later-approved assets. The separate home-page halal-catering section and the `SingPost (Halal)` and `Pandan Loop (Halal)` outlet labels must remain unchanged.

## Acceptance Criteria

- All twelve legacy menu names map to the approved supplied tiers without customer-facing renaming.
- Every mapped menu contains the complete supplied dishes, choices, dietary notes, and add-ons in the intended order.
- Displayed prices, minimum quantities, course counts, cart base totals, and per-pax add-ons agree with the approved source.
- Set and DIY A–D and Vegan A–D can each render, accept valid selections, and add the correct menu to the cart.
- The twelve menus contain no halal claim or label and do not introduce a non-halal badge.
- Existing public URLs for current menus remain valid; the new Vegan D URL is documented and linked from the collection page.
- Existing M2.4 smoke coverage remains green, with M3.3 adding menu-specific regression checks.
- All 20 supplied images are accounted for as approved replacements or KIV, while image implementation remains a separate reviewed step.
