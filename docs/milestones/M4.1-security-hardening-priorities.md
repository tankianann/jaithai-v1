# M4.1 — Security Hardening Priorities

**Status:** Implemented

**Delivery phase:** Phase 4 — Constrained modernization

**Roadmap:** [`../roadmap/roadmap.md`](../roadmap/roadmap.md)

## Outcome

Establish an evidence-based security risk register for the legacy production application while retaining PHP 7.4 and CodeIgniter 2.2.2, and distinguish non-invasive deployment hygiene from changes that should be kept in view for v2.

## Stability Decision

The application has operated for approximately ten years without an observed incident, and a replacement v2 is in development. At the user's direction, any security change that could alter routes, authentication, sessions, forms, integrations, generated documents, or existing operational workflows is KIV rather than an implementation target for v1.

The absence of an observed incident does not prove that the identified exposures are harmless. For this project it does change the delivery decision: document the risks, avoid destabilizing v1, keep outbound integrations guarded, and carry the findings into v2 by design.

## Constraint and Risk Posture

PHP 7.4 reached end of life on 2022-11-28 and no longer receives normal security fixes, so application-level changes can reduce exposure but cannot turn this stack into a current security baseline. The official [PHP unsupported-branches page](https://www.php.net/eol.php) recommends upgrading unsupported releases because fixed vulnerabilities and bugs remain present.

The project constraint still requires PHP 7.4 and CodeIgniter 2.2.2. M4.1 therefore prioritizes reducing reachable attack surface, strengthening authentication and request integrity, and containing sensitive generated data without attempting a framework or runtime migration.

## Evidence Reviewed

- Authentication and access control in `application/core/KA_Controller.php`, `application/models/users_model.php`, and `application/controllers/jtadmin.php`.
- Public and operational controllers in `application/controllers/api.php`, `application/controllers/cron.php`, `application/controllers/kianann.php`, and `application/controllers/ajax.php`.
- Session, cookie, CSRF, encryption, and database configuration in `application/config/config.php` and `application/config/database.php`.
- Order creation, public acknowledgement links, generated documents, and serialized cart data in the cart, order model, helpers, administration views, and email/PDF views.
- Apache rules, repository ignore rules, tracked integration guards, and the two untracked ZIP archives currently located inside the web root.
- Existing local regression and smoke coverage, including the protected configuration, administration fixture, representative carts, and generated PDF checks.

## KIV — Public Exposure Containment

### Unprotected Administration AJAX Methods

The main administration actions call `limitAccess()`, but `jtadmin/ajax`, `jtadmin/ajaxusevoucher`, `jtadmin/ajaxorderremoveitem`, and `jtadmin/sendordersms` do not. These methods can retrieve order or voucher data, select a server-side view from a submitted operation name, and trigger an SMS without the administration access check.

If v1 receives security changes later, place every administration endpoint behind an explicit permission check, replace the submitted view-name dispatch with an allowlist, and add negative smoke tests proving unauthenticated requests are rejected. This is KIV because existing administration JavaScript and workflows may depend on the current behavior.

### Public Order API

`api/orders/get/:orderid` returns an order by numeric ID without authentication, and `api/orders/add` accepts JSON order and cart data, creates a database record, and invokes order email delivery. Repository search found no in-application caller, but an external production consumer cannot be ruled out from source alone.

For v2, require authenticated, rate-limited, schema-validated endpoints and avoid exposing raw order records. Disabling or changing the v1 controller is KIV because an external production consumer cannot be ruled out from source alone.

### Public Operational Controllers

`cron/sms_orders_today` can initiate customer SMS delivery without authenticating the caller. The `kianann` controller contains report, customer-data, PDF-generation, and SMS routines that are reachable through normal CodeIgniter controller routing and include historical one-off operations.

For v2, make utility actions unavailable in production and place scheduled work behind a private server-to-server boundary. Disabling or changing the v1 controllers is KIV because undocumented operational use cannot be ruled out; the existing outbound-integration master switch must remain the safety boundary.

### Web-Root Archives

`src/application.zip` and `src/assets/Archive.zip` are local files inside the served web root. The application archive contains the application source tree and both files would be ordinary static files if copied to production.

The archives were not modified during this assessment. Their exact paths are now ignored to prevent accidental commits, and they must be excluded from every production copy. Moving or deleting them requires the user's separate direction; Apache rule changes are KIV because production compatibility is the controlling concern.

## KIV — Authentication and Request Integrity

### Administrator Identity Cookie

The application serializes the administrator record into the client-controlled `jtloginuser` cookie and calls PHP `unserialize()` before integrity verification. The record includes the stored password hash and role/scope fields. OWASP recommends avoiding native deserialization of untrusted input because it can enable denial of service, access-control bypass, or code execution depending on available classes; see the [OWASP Deserialization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html).

For v2, use server-side session identity containing only a user identifier, regenerate the session on login, and require database lookup for the current role and scope. Changing the v1 login cookie is KIV because it would force an authentication migration and could interrupt administration access.

### Password Storage

Administrator passwords use SHA-1 with a fixed salt embedded in source. V2 should use `password_hash()` and `password_verify()` with a controlled account migration or reset. Changing v1 password storage is KIV because compatibility and recovery behavior would need production testing.

### CSRF and Unsafe Mutations

Global CSRF protection is disabled while many authenticated administration operations mutate orders, vouchers, emails, PDFs, and SMS state. Some mutations are addressable through route parameters rather than an authenticated form token.

V2 should protect every state-changing request, use POST semantics, and reject missing or invalid tokens. Enabling CodeIgniter CSRF protection in v1 is KIV because every legacy form and AJAX request would need coordinated changes and regression testing. OWASP notes that authenticated cookie-based applications cannot distinguish forged cross-site requests without a request-integrity mechanism; see the [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

### Cookie Transport Settings

The tracked configuration sets `cookie_secure` to false, does not establish a SameSite policy, keeps session data in a client cookie, and does not enable session-cookie encryption. V2 should use Secure, HttpOnly, and an explicit SameSite policy. Changing v1 cookie behavior is KIV because the NGINX-to-Apache HTTPS signaling and legacy session behavior would require production-parity validation; see the [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

## KIV — Sensitive Order Artifacts

Generated invoices, receipts, food tags, timestamps, envelopes, labels, and vouchers are written below `assets/pdf/` and linked as static files. Their names derive from order or voucher numbers, and the current smoke suite confirms that a generated PDF is publicly retrievable without administration authentication.

V2 should store sensitive documents outside the public web root and deliver them through access-controlled or short-lived download grants. Changing the v1 document path or delivery flow is KIV because administration and email workflows rely on the current files.

Order acknowledgement and feedback URLs use a deterministic SHA-1 value derived from an order number and a fixed source-code salt. V2 should use cryptographically random, stored tokens with suitable expiry or one-time-use rules. Changing v1 tokens is KIV because already-issued customer links must remain compatible.

## KIV — Output, Input, and Abuse Resistance

- Audit every customer and administrator view for contextual output encoding. The shared `_e()` helper currently echoes without escaping, while customer-supplied order fields are rendered in HTML, email, and PDF contexts.
- Add strict request schemas and server-side choice validation rather than trusting submitted menu labels, prices, cart structures, operation names, and order identifiers.
- Add login throttling and rate or volume controls to order creation, address lookup, email, SMS, PDF, and feedback endpoints.
- Constrain PHP `unserialize()` for database-held cart data with `allowed_classes => false` where PHP 7.4 supports it, then plan a versioned JSON representation for new records while retaining explicit legacy reads.
- Inventory security headers at the NGINX and Apache layers, then add only headers compatible with the current frontend and external assets.
- Keep legacy Clickatell and Elastic Email transports disabled until their insecure transport behavior is removed or the integrations are retired.

## Verification Requirements

- Extend automated checks before each behavior change so unauthenticated access, CSRF failures, role boundaries, token handling, and document denial have explicit regression coverage.
- Keep the 173 menu regression checks and 106 baseline smoke checks green.
- Test production-style HTTPS proxy headers locally before enabling Secure-cookie behavior.
- Use only synthetic fixture records and disabled outbound integrations during security tests.
- Review deployment instructions so protections at NGINX, Apache, and application layers cannot silently diverge.

## Non-Invasive V1 Actions

- Keep the exact ignore rules for `src/application.zip` and `src/assets/Archive.zip`, and do not copy either archive to production.
- Keep outbound integrations disabled in development and enable them in production only through the existing private configuration switches.
- Retain the existing smoke and menu regression suites for every v1 content or maintenance change.
- Use this risk register as an explicit security checklist for v2 architecture and acceptance tests.
