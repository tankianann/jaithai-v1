# M4.2 — URL Contract and V2 Migration

**Status:** Implemented

**Delivery phase:** Phase 4 — Constrained modernization

**Roadmap:** [`../roadmap/roadmap.md`](../roadmap/roadmap.md)

## Outcome

Define controller-independent canonical URLs for v2 and a one-to-one migration from both legacy `.php` aliases and current CodeIgniter controller routes, without risking the final month of v1 operation.

## Findings

- V1 has three simultaneous URL layers: historical `.php` aliases, native CodeIgniter `/controller/method` paths, and a small number of root or service URLs.
- `routes.php` defines only the home page, so almost every current native URL exposes controller and method names.
- Adding clean CodeIgniter aliases would be low risk, but aliases alone would not stop the controller URLs from remaining reachable or being indexed.
- Redirecting or blocking controller URLs in v1 would be materially riskier because menu forms post back to their current route, administration JavaScript calls `/jtadmin/...`, payment and customer links use `/cart/...`, and seasonal cart JavaScript contains absolute production URLs.
- Permanent redirects are cached and are difficult to reverse safely during a one-month replacement window.

## Decision

Do not change v1 route behavior. Treat the clean paths documented in [`../development/url-routing.md`](../development/url-routing.md) as the v2 URL contract, and implement the redirects as part of the v2 launch.

V2 must not expose implementation names such as `jtpages`, `jtmenu`, `cnymenu`, `xmasmenu`, `specialmenu`, `cart` action methods, or legacy `.php` filenames in generated navigation. Administration and integration endpoints should also be explicitly routed rather than derived automatically from controller class names.

## Migration Rules

1. Each historical `.php` URL and each current CodeIgniter URL must map directly to one final v2 canonical URL.
2. Do not redirect `.php` URLs to controller URLs and then to v2; remove the existing intermediate hop at cutover.
3. Use server-side permanent redirects only for GET and HEAD page requests after the destination has been verified.
4. Do not rely on redirects for POST forms, payment callbacks, API requests, or administration mutations. Update their producers and consumers to the v2 endpoint contract before launch.
5. Preserve required query parameters, especially customer acknowledgement and feedback tokens, while translating parameter names only when v2 explicitly supports both forms.
6. Return a true 404 or 410 for retired content without an equivalent page instead of redirecting unrelated content to the home page.
7. Generate only canonical URLs in v2 internal links, forms, emails, PDFs, structured data, canonical tags, and the sitemap.
8. Keep the final redirects for at least one year and preferably for the remaining life of the domain.

Google's [site-move guidance](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes) recommends preparing a complete old-to-new mapping, updating internal links, using server-side permanent redirects, and avoiding redirect chains. It also recommends retaining redirects for at least one year.

## V1 Work

- Keep the existing `.php` and controller routes unchanged.
- Keep the current smoke suite as the v1 URL regression gate.
- Use server logs and Search Console to identify externally used or high-traffic URLs that source inspection cannot reveal.
- Do not introduce new public controller-style URLs during the final month.

## V2 Work

- Implement the canonical public routes and named route generation before importing page templates.
- Update forms and internal navigation to submit directly to canonical v2 endpoints.
- Separate browser pages, customer token actions, administration routes, and machine integrations into explicit route groups.
- Generate a canonical sitemap containing only indexable public GET pages.
- Add automated route-contract tests for canonical responses, old-path redirects, query preservation, method restrictions, and retired URLs.
- Validate the redirect table against production access logs, analytics landing pages, Search Console links, email templates, PDF templates, payment settings, scheduler configuration, and third-party callbacks before launch.

## Acceptance Criteria

- Every supported v1 public page has exactly one documented v2 destination.
- No v2 customer-facing link exposes a controller or method name.
- All old `.php` and controller-style page URLs redirect in one hop to the correct canonical destination.
- POST, callback, administration, and API consumers use the correct v2 endpoint directly rather than depending on a 301 or 302.
- Canonical tags, sitemap entries, and internal links agree on the same URLs.
- Retired content returns 404 or 410 unless a genuinely equivalent replacement exists.
- Automated tests cover the full redirect matrix before DNS or origin cutover.

## Explicit Exclusions

- No v1 route, redirect, controller, form action, payment callback, or internal link is changed by this milestone.
- No v2 code is present in this repository, so implementation remains a v2 launch task.
- Administration URL redesign is documented as a route-group principle rather than a complete workflow redesign.

## Remaining Work

- Review the proposed canonical URL names with the v2 implementation.
- Supplement the source-derived inventory with production access logs and Search Console data.
- Commit this documentation milestone.
- Implement and test the mapping in v2 before launch.
