# M2.2 — Add the Local Database Schema Bootstrap

**Status:** Complete

**Delivery phase:** Phase 2 — Reproducible local runtime

**Roadmap:** [`../roadmap/roadmap.md`](../roadmap/roadmap.md)

## Outcome

A developer can destructively reset the Docker-local `jaithai` database and recreate the production-compatible five-table structure without possessing or importing production rows.

## Scope

- Inspect the externally stored production dump without copying it into the application repository.
- Extract only table definitions, keys, engines, character sets, and collations through an isolated MariaDB 10.11 environment.
- Remove production auto-increment positions and all row data from the tracked artifact.
- Add a simple PHP 7.4-compatible reset command using the existing Docker-local configuration.
- Require explicit destructive intent and reject non-development or unexpected database targets.
- Document database reset usage, limitations, provenance, and the production-data boundary.

## Constraints

- Never add the production dump or production-derived rows to Git.
- Do not load production rows into the persistent local Docker volume.
- Preserve the current production schema rather than modernizing it during extraction.
- Do not add a general incremental migration framework.
- Do not add synthetic data in this milestone.

## Acceptance Criteria

- `database/schema.sql` defines all five production tables and contains no `INSERT`, credential value, customer record, or production auto-increment position.
- The schema reproduces the production-derived column, key, engine, character-set, and collation structure.
- The reset command refuses to run without `--force`.
- The reset command refuses to run outside the `development` environment or against an unexpected database name.
- A forced reset removes existing local objects, applies the schema, and succeeds repeatedly.
- All resulting tables are empty.
- The application and independent health endpoint remain reachable after reset.

## Verification

Implemented and verified on 2026-10-01:

- Inspected a 30,658,164-byte external SQL dump containing five tables, 631 data inserts, and no views, triggers, routines, events, `DEFINER` clauses, database creation, or `USE` statement.
- Imported the dump into a network-disabled temporary MariaDB 10.11 container backed by tmpfs, exported structure only, and destroyed the container.
- Compared a schema-only dump of the recreated local database with the production-derived structure after normalizing production auto-increment positions; no differences remained.
- Confirmed that an invocation without `--force` exited with code 64 and did not reset the database.
- Ran two consecutive forced resets; each recreated five tables successfully.
- Inserted a harmless local probe row, reset the database, and confirmed all five tables were empty with auto-increment positions reset to 1.
- Confirmed `bin/migrate.php` passed PHP 7.4 syntax validation.
- Confirmed the reset works both as `php bin/migrate.php --force` on the host through `127.0.0.1:3307` and through the web container, without reading the ignored private configuration.
- Confirmed `/__health` and the application front page both returned HTTP 200 after reset.
- Gitleaks v8.30.1 scanned the candidate tree with the ignored private configuration excluded and reported no leaks.

## Exclusions

- Production or customer data.
- Synthetic development fixtures.
- Forward-only migration history, rollbacks, and automated schema-diff tooling.
- Changes to legacy table engines, character sets, collations, or column definitions.
- End-to-end database-backed application testing.
